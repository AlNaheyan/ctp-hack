# W3-T4 Submission and Loading Handoff

## Configuration and HTTP boundary

The macOS app reads `DISCUSSION_API_BASE_URL` from its process environment and
defaults to `http://127.0.0.1:8787`. The client calls:

```text
POST {baseURL}/v1/analyze
Content-Type: application/json

{"url":"https://www.youtube.com/watch?v={videoId}","forceRefresh":false}
```

`URLSessionDiscussionAnalysisAPI` uses a 45-second per-request timeout. A `202`
processing response is retried using `retryAfterSeconds` or `Retry-After`, clamped
to 0.25–30 seconds. Success responses are decoded with `DiscussionJSON`, validated,
and rejected unless their video ID matches the submitted URL.

## Public interfaces

- `DiscussionAnalysisAPI` is the injectable transport boundary.
- `URLSessionDiscussionAnalysisAPI` implements the W3-T1/mock HTTP contract.
- `DiscussionAnalysisCoordinator` owns cache-first submission, refresh, retry,
  logical cancellation, typed loading state, and `DiscussionSessionState` activation.
- `DiscussionAnalysisCoordinator.receive(_:)` is the W3-T2 playback hook. It
  returns only timeline events emitted for matching video playback; W3-T3 may
  enqueue/present those events.
- `DiscussionSessionModel.receivePlayback(_:)` is the existing app-level bridge
  and currently maps emitted package events into the notch insight card.

The app links the local `Packages/DiscussionTimeline` product. No cache persistence
is duplicated: the coordinator uses `DiscussionTimelineCache` and
`FileDiscussionCacheStorage` at W2-T4's default location.

## Cancellation and replacement rules

- Every accepted submission cancels the prior task and receives a new request ID.
- Late responses are ignored unless their request ID is still current.
- The previous valid timeline remains loaded during submission and error states.
- A replacement becomes active only after contract validation and video-ID matching.
- Cancel restores the previous ready state (or Empty when none exists).
- Refresh and Retry bypass the local cache and send `forceRefresh: true`.
- A valid response still activates if its local cache write fails.

## Typed recovery mapping

- URL validation failures: inline invalid-URL state; no request is sent.
- DNS/connectivity/transport timeout: Offline with explicit Retry.
- Private, missing, caption-disabled, unsupported-language, or transcript-unavailable:
  No transcript/video unavailable; retry follows the server's `retryable` flag.
- Analysis/provider/internal failures: Backend error; retry follows `retryable`.
- Unsupported schema: Update required; Retry is disabled.
- Malformed, contract-invalid, or mismatched success: Invalid response with Retry.

## Verification checklist

- [x] Fixture URL supports Empty → Submitting → Processing → Ready.
- [x] A valid local cache hit activates without calling the API (offline-safe).
- [x] Manual refresh bypasses the cache and replaces it with a valid response.
- [x] Mismatched response video IDs neither activate nor enter the cache.
- [x] Repeated submissions ignore a superseded late response.
- [x] Package tests pass: `swift test --package-path Packages/DiscussionTimeline`.
- [x] Unsigned macOS app build passes with the local package linked.

For manual mock verification, run `npm run dev`, submit
`https://www.youtube.com/watch?v=demoTalk001`, then stop the backend and submit
the same URL again to verify the local cache. Use Refresh while the backend is
stopped to verify the Offline recovery state.
